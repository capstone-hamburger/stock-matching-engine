# ADR-001: PriceLevel을 통한 가격별 호가 잔량 관리

- 상태: Accepted (구현 및 테스트 검증 여부는 별도 확인)
- 범위: C++ Matching Engine / OrderBook

## 배경 및 문제

기존 OrderBook은 매수·매도 가격별로 `std::deque<OrderId>`를 관리한다. 같은 가격에 여러 주문이 존재하면, 외부에 제공할 호가 잔량을 계산하기 위해 각 `OrderId`에 대응하는 주문의 미체결 수량을 조회하고 합산해야 한다.

이 방식은 해당 가격대에 속한 주문 수가 늘어날수록 호가 조회 비용도 증가한다. 한 가격대에 주문이 `M`개라면 잔량 합산은 `O(M)`이다.

## 검토한 대안

1. **조회 시 합산:** 기존 자료구조를 유지하고, 호가 조회 시마다 주문별 미체결 수량을 순회해 합산한다.
2. **가격별 잔량 유지:** `PriceLevel`에 주문 ID 목록과 `totalQuantity`를 함께 저장하고, 주문 상태 변경 시 잔량을 증감한다.

## 결정

`std::map`의 value를 `std::deque<OrderId>`에서 `PriceLevel`로 변경한다. `PriceLevel`은 동일 가격대의 주문 ID 목록과 총 미체결 잔량을 관리한다.

```cpp
struct PriceLevel {
    Quantity totalQuantity = 0;
    std::deque<OrderId> orderIds;
};
```

잔량은 다음 시점에 갱신한다.

| 상황 | `totalQuantity` 갱신 |
| --- | --- |
| 신규 주문의 미체결 잔량을 OrderBook에 등록 | 등록 수량만큼 증가 |
| 기존 대기 주문의 부분·완전 체결 | 체결 수량만큼 감소 |
| 기존 대기 주문 취소 | 남은 미체결 수량만큼 감소 |
| 가격대의 주문이 모두 제거됨 | 빈 `PriceLevel` 제거 |

신규 주문이 접수되더라도 즉시 전량 체결되어 OrderBook에 등록되지 않는다면 해당 방향의 가격대 잔량은 증가하지 않는다.

## 기대 효과와 Trade-off

- **장점:** 특정 가격대의 총 미체결 잔량 조회가 `O(1)`이 된다. 상위 N개 가격대의 잔량을 조회할 때 각 주문을 다시 순회할 필요가 없다.
- **비용:** 주문 추가·체결·취소 경로에 상수 시간의 잔량 갱신이 추가된다.
- **위험:** 개별 주문의 `remainingQuantity`와 `PriceLevel.totalQuantity`가 불일치할 수 있으므로 모든 변경 경로에서 함께 갱신해야 한다.
- **제약:** 이 변경 자체가 매칭 처리량 또는 지연시간 개선을 보장하지는 않는다. 실제 효과는 벤치마크로 확인한다.

## 검증 항목

- 신규 주문 등록, 부분 체결, 완전 체결, 주문 취소 이후 `totalQuantity`가 정확한지 확인한다.
- 테스트에서 각 가격대의 주문별 `remainingQuantity` 합계와 `totalQuantity`의 일치를 검증한다.
- 빈 가격대가 제거되는지, 매수·매도 가격 우선순위와 동일 가격대 FIFO 순서가 유지되는지 확인한다.
- 필요 시 기존 조회 시 합산 방식과 호가 조회 비용 및 주문 처리 지연시간을 비교한다.

## 향후 고려 사항

- Market Data Publisher에 상위 N개 호가를 제공할 때 `totalQuantity`를 활용한다.
- 주문 로그 재생이나 상태 복구를 도입할 경우 동일한 잔량 갱신 규칙을 적용한다.
